# install

The installation engine: it moves a machine to the state a selection record describes, one installer per component of the `internal/components` catalog. `Plan` previews the steps, `Apply` runs them, `Status` reports per-component health.

## How it works

**Record and apply**
- The selection record (`install.json` in the state dir of the Claude home, schema 2) holds the preset, the component ids, the skill selection — mode, the chosen leaves, `confirmed`, which makes the terminal installer keep the selection instead of asking (its `-reset-skills` and the Profile page's Installer tick clear it), `variables`, the `SKILL_*` values the skills sync fills, `defaults`, one global default per repo-scoped interface id (the Environment tab's card), `providers`, the `PROVIDER_*` program overrides, and `suspended`, chosen leaves whose required component is off — and `settings`, the overrides only: component id → setting key → the value in its kind's JSON form. Defaults stay in the `internal/components` catalog. A machine without the file is treated as the full preset. Ids the catalog retired since the record was written move to `retired` on load and stay there; a Profile apply starts from the stored record and changes only the ticked components — unticking a component moves its dependents to `suspended.components`, ticking it again brings them back; turning Routines or Mining off stops the routines they own (Mining: smine-nightly) and lists their labels in `suspended.routines`; a later apply starts each once Routines is on again, and smine-nightly once Mining is too.
- `Validate` refuses a value its kind refuses; an unknown component or key, a key of an unselected component, or a group row whose group the fragment dropped, is kept inert, never fatal — `Notes` lists the retired ids and unknown entries for the Profile page. `Resolve` is a setting's effective value (override, else default; a group row's default is the fragment's), `InstallValues` the typed view of the `install` sink rows — ports, peek homes, server path, count tokens, init welcome — that `Env.Values` carries. `Schema` lists a component's rows: the catalog's static rows, then `groups.<smineId>.timeout|matcher|async` per hook group of its fragment.
- `Validate` refuses every schema but 2; there is no import of an older record.
- `Apply` saves the record with `applied: false` before the first step, installs the selected components in catalog order, removes the unselected ones in reverse catalog order, then re-reads the record and saves it with `applied: true`. It returns one result per component.
- A component whose plan holds no steps is unchanged. A config-server plist change reports `restart-required`; the caller restarts the server.

**Sync targets**
- `SyncTargets` runs a picked subset of the record's deploy without the rest of `Apply`, in `SyncTargetOrder` — settings, hooks, skills — stopping at the first failure; each target's output is headed `== <target>` on `env.Stdout`.
- `settings` is `ApplySettings`: base keys added where absent, every component's fragment moved in or out of `~/.claude/settings.json` and `~/.claude.json` by the record.
- `ForcePreview` lists every live key, group, env key, permission entry and parked group a rebuild would drop, for the confirm the config page shows first. `ForceSettings` (the config page's Force sync, after that confirm) replaces `~/.claude/settings.json` with base plus the selected components' fragments composed from the template, empties the parked hooks sidecar — both previous files kept in the trash, the journal counting what went — and reconciles `~/.claude.json`'s MCP servers as `ApplySettings` does — the reset for a live file that accumulated hook groups, rules and keys no template file declares.
- `hooks` is `ApplyHooks`: the hook binaries of the selected components only — no PATH binaries, files, settings or extras.
- `skills` is the record's skill sync, the Skills component's own extra; without that component selected it deploys nothing.
- `all` is the full `Apply` and wins over any other target in the same call; the config server routes it through the Profile page's apply, restart included.

**One installer implementation**
- Every component is an `artifactComponent` declared by data: binaries, repo files, the settings fragment named by its id, custom extras and an optional liveness probe.
- Binaries: Rust programs come prebuilt from the checkout's `bin/`; Go programs are built from `cmd/<name>` in a development checkout and read prebuilt from `bin/` in an extracted release archive, which `bin/PAYLOAD` marks (`payload.go`, `Env.IsPayload`) — a development checkout without `go` on PATH is an error. Hook binaries land in `~/.claude/hooks/bin/<name>` without a suffix on every OS; PATH binaries (rules, agentwt, heartbeat, routine) land in the smine bin dir `config.SmineBinDir` on every OS — `~/go/bin/smine-<name>`, on Windows `%LOCALAPPDATA%\smine\bin\smine-<name>.exe`, the dir `-install` registers on the user PATH.
- Ownership: a copied file is smine's while its sha256 equals the digest under `owned/` (written on every copy), a binary or rendered file by name. An update overwrites an owned target only, its previous bytes kept in the trash (binaries excepted); a target that is not owned is reported `kept` and left alone, so a user's own `~/.claude/AGENTS.md` survives.
- Removal moves every owned target into the trash; nothing is deleted.
- Health is a cheap presence check of targets and settings entries, never a build, followed by the optional probe.

**Settings reconciliation**
- A component's fragment (`settings/claude_code/components/<id>`) is merged into `~/.claude/settings.json` and `~/.claude.json`; both are loaded once per reconcile and saved only when something changed. `~/.claude.json` is written 0600 because it holds harness credentials.
- Every fragment hook group carries `smineId` (prefixed by its component id, unique across all fragments), `smineName` (its display name, 1 to 32 runes) and `smineVersion` (a three-part semantic version above `0.0.0`); a fragment group without them, or one declared twice, fails the load. A live group's legacy integer version reads as that major release (`1` is `1.0.0`), so a fragment at `1.0.1` replaces it. Live groups are matched by id: a missing id is added, a lower live version is replaced in place, an equal or higher one stays as it is (its timeout, matcher and async re-rendered, its command kept), an unselected component's live groups are parked in `hooks.disabled.json` with `smineReason: "component off"` and come back live when it is selected again (a user's own park, without the reason, stays parked) — so a changed group command or name bumps `smineVersion`, which the `fragment-check` audit unit (`smine-rules fragment-check`) enforces against the branch base. A group parked in the `hooks.disabled.json` sidecar counts as present and is replaced there, still parked, when outdated.
- After every reconcile a prune pass removes each group whose id the repo's retire list `settings/claude_code/retired-hooks.json` names, live and parked alike, with a journal line; every other group stays, and a missing list retires nothing. A group without an id is the user's and is never touched, whatever it runs. Keyed entries (env keys, MCP servers) are added when absent and removed only while they still equal the fragment's value, each removal journaled.
- Base keys are added where absent, recursing into objects both sides hold; a present value is the user's and stays, as does a live key the template does not carry. The permission lists `base.json` may hold are reconciled like a fragment's: missing entries are added, live extras stay.
- The reverse direction, the config page's Persist overrides (`PersistSettings`), writes the live `settings.json` back into the template: an env key a component fragment declares goes to that fragment, the unowned entries of an owned permissions list and every other key go to `base.json`, which afterwards holds exactly the live keys no fragment owns; hook groups are never written back. Install markers are collapsed against the file's previous bytes.
- Rendered files, never copied: `~/.claude/hooks/config.json` (the `hooksConfig` sink, written by the Session hooks component; applying any other component with hooksConfig rows applies Session hooks too) and `~/.claude/heartbeat/config.json` (the `heartbeatConfig` sink, plus `peek_addr` derived from `peek.port`) are marshalled from the catalog defaults plus the record's overrides, keys sorted, durations as `<key>_ms` integers, and written when the bytes differ. The `hooks` sync target renders the hooks config with the hook binaries.
- `hookGroup` overrides (timeout, matcher, async) are set on the fragment's raw group before the smineId match. The three fields are render-owned: every apply copies them from the fragment plus overrides onto a live group of the same version and leaves the rest of that group as it is, so a cleared override reverts at once.
- Restart class: the heartbeat agent is restarted when the plist changed, the agent is unloaded, or a `restart` row's value (or `peek_addr`) differs between the deployed config and the rendered one; a `live` row reaches the daemon through its config watch.

**Extras**
- Routine plists are rendered from their templates once, `__REPO_DIR__` filled with `Env.MainRepoDir` (the main checkout `gitroot.MainRoot` resolves from the applying checkout, so a worktree apply never embeds the worktree); an existing plist is operator state, which only `configserver -refresh-routine-plists` reconciles from its template. Routine jobs, the nightly included, are only stopped — when Routines or the Mining pipeline is turned off; loading them is the config server's boot sync, which skips a label the operator disabled.
- A launchd agent is restarted by booting it out, waiting until launchd dropped it, then bootstrapping it. `-install` restarts the config server and heartbeat agents unconditionally on darwin, since it rebuilt their binaries; `-apply` builds nothing and restarts an agent only when its plist changed or it is unloaded.
- The heartbeat extra branches on the OS: darwin writes the LaunchAgent plist, Windows registers the logon task `\smine\com.smine.heartbeat` from `routines.LogonTaskXML` (the config server task's template) running `<main checkout>\bin\heartbeat.exe` with the plist's flags plus `--log-file %LOCALAPPDATA%\claude-routine\logs\heartbeat.log`. The task is due when it is not registered or a `restart` row changed; installing stops a running instance first, since `Register-ScheduledTask -Force` replaces the definition, not the process; removal stops and unregisters it. `-install` re-registers it after the apply (`RestartHeartbeatService`).
- Skill sync deploys the record's skill selection and moves marked skill dirs outside it into the trash; mode none deploys nothing, so it and the component's removal move every marked dir — a skill dir without the marker is never pruned, and one under a deployed name is stashed whole before the write.

**Trash**
- `Env.Trash` is the `internal/trash` store under `~/.claude/smine` (see its README): every removal and replacement of this package goes through it — retired targets, rewritten copies, the codex config, the previous `settings.json`, `~/.claude.json` and parked file — with a journal line in `journal.jsonl`.
- `Save` keeps the record's previous bytes beside it as `install.json.<stamp>` (newest 50 kept, listed by `History`) and refuses, under the file lock, a record whose `updated` stamp differs from the stored one with `ErrRecordChanged`, so a writer that loaded a stale copy reloads instead of overwriting a newer save.
