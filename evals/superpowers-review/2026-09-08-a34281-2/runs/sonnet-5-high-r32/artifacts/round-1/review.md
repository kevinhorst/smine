# Review: smine v1.1.4 → v1.2.1 (b4981b88 → a342811b)

Scope: 178 files, +7314/-749, excluding `sessions/`, `evals/`, `proposals/`, `plans/`. Reviewed against the 9 plan documents under `plans/v1-2-1/`. This diff bundles multiple independent change plans (ACDSL policy modes, repo cache/deletion, repos+routines UI, bootstrap wrapper rewrite, presentation/i18n, peek multi-profile, plan-format viewer fixes, session-context report, smine-profile-settings) landed as one release range.

**Method:** Given the size, this was reviewed in passes: (1) full plan reading for all 9 plan dirs, (2) file-by-file diff review of every Go package touched, weighted toward the risk tiers in ACTION-REVIEW-RISK-001 (the ACDSL policy engine, the repo registry, launchctl/routines, the row-verdict cache and safety-gate shell logic), (3) lighter-touch reading of templates, docs, and skill Markdown, (4) independent verification by building and testing a **clean worktree checked out at the exact head commit** (the assigned `arm-wt` checkout carries pre-existing uncommitted local modifications to `acdsl/{policy,registry}.json` and `acdsl/rules.acdsl` predating this review session — not caused by my review actions, and excluded from all conclusions below; see the note under Critical).

## Strengths

- **ACDSL policy engine (`internal/acdsl/policy.go`)** is well designed and closes a real hole in its own plan's pseudocode: the plan's `CheckPolicy(ctx, root, policy)` reads `policy.Mode` from the *working-tree* file and returns early on `free` before ever computing the surface diff — meaning an agent could edit `acdsl/policy.json` to `"mode": "free"` and defeat every check, including detecting that very edit. The implementation fixes this by resolving the base ref first and re-reading the **base-ref-authoritative** policy (`basePolicy`) before deciding whether to gate — and there's an explicit regression test for exactly this scenario (`TestCheckPolicyBaseModeSurvivesWorkingWeakening`, `policy_test.go:185`). This is a deliberate, tested improvement over the plan; worth confirming it was intentional (it clearly reads that way) rather than accidental.
- Policy engine test coverage is thorough: 16+ table cases plus dedicated tests for the vacuous-on-base-branch case, unresolvable-base hard error, task-contract exemption, and the untracked-new-policy-on-branch case.
- **Registry read-through** (`internal/repos/registry.go`) matches its plan closely: stat-guarded reload, read-modify-write `Add`/`Remove` against a fresh snapshot (closing the stale-in-memory-slice resurrection bug), degrade-and-log on a bad hand edit at read time vs. loud failure at startup. Tests cover external-edit visibility, cross-instance delete durability, and truncated-file degradation.
- **Status-cache fingerprinting** (`internal/server/statuscache.go`, `repos.go`) is a clean, minimal mechanism (two fast git reads) that gives a one-sentence answer to "when does this reload" and is fully covered, including the `DropBranches` pre-removal-fingerprint-kept trick that makes the optimistic-delete UI converge to scan truth on the next load.
- **Squash-containment layer 4** in `cmd/worktrees/_lib/verdict.sh` (`squash_contained`, the `evaluate_branch` sweep) is conservative by construction — a `git merge-tree` failure or tree mismatch fails safe to "still unpicked," never to a false "safe to remove." This feeds the branch-removal safety gate, so the fail-safe direction matters; it's correctly fail-safe and has both a positive (squash-transferred) and a negative (edited-after-squash stays unpicked) shell test.
- The **new per-branch verdict row cache** under `<git-common-dir>/agent-status-cache/` (mkdir'd once in the parent before the parallel `xargs -P` row workers, atomic `mktemp`+`mv` per file, candidate-tip digest invalidation, stale-branch pruning) is correct for the concurrent-writer case and has unusually good test coverage for a shell feature: warm-hit, bypass, truncated-file-is-a-miss, candidate-movement invalidation, and deleted-branch pruning are all exercised in `test_print_agent_worktrees_status.sh`.
- **`cmd/hooks/skill-invoke-gate.sh`** (new) is a careful, fail-open piece of infra with a matching 9-case shell test suite covering pre/post-invocation, wrong-skill-doesn't-satisfy, the headless prompt-start-slash path, and the context-read denial with its language-guide exemption.
- **`peek.SessionIndex`** correctly implements the documented fix (FACT-REPO-ARCH-017): branch identity (`ByBranch`) is tried before the recycled-worktree-dir fallback (`ByCwd`) in `worktreeSessions` (`repos.go`).
- The **bootstrap wrapper rewrite** (`cmd/bootstrap/run.sh`) matches its plan closely, including the fail-forward-per-stage / orchestrate-is-terminal-arbiter design (D7), deterministic env→flag translation (D5), and default-deny dev-mode derivation (casual audience always forces `dev_mode` off, `D3`).
- **Build, `go vet`, and the full Go test suite pass cleanly** on a from-scratch checkout of the exact head commit (`a342811b`), as do the targeted shell suites for every area touched (`test_print_agent_worktrees_status.sh`, `test_remove_agent_worktrees.sh`, `test_skill_invoke_gate.sh`, `test_bootstrap_wrapper.sh`, `test_sync_skills_overrides.sh`, `test_read_gate.sh`).

## Issues

### Critical (Must Fix)

None found in the reviewed range on a clean checkout.

**Note on a false alarm surfaced during review:** `go test ./...` in the assigned `arm-wt` checkout fails one test, `TestDistShipsReachCoveredSliceWithBinaries` (`internal/acdsl/dist_test.go`), with `stat .../bin/verifiers/gofmt: no such file or directory`. This is **not a defect in the reviewed diff** — `git status` in that checkout shows pre-existing uncommitted local modifications to `acdsl/policy.json`, `acdsl/registry.json`, and `acdsl/rules.acdsl` that predate this review session (I did not write to these files; my only writes were to the scratch worktrees I created for verification). Those local edits rewrite every registry entry's `argv` from the `["go","run",...]` shape to a prebuilt `bin/verifiers/<name>` path, which starves `writeDistRegistry`'s rewrite branch and so `buildBinaries` never builds `gofmt`. On a freshly checked-out copy of the actual head commit (`a342811b`, clean tree) the same test passes, and the full suite is green. Flagging this so it isn't mistaken for a regression by a later pass — the assigned working checkout should be reset before it's reused for anything that depends on `acdsl/registry.json`.

### Important (Should Fix)

1. **Settings-wide `ask` gate for ACDSL rule/registry edits was removed globally, and the loss isn't called out anywhere in the ACDSL policy plan.** `settings/claude_code/settings.json` (`permissions.ask`) previously required interactive confirmation before any `Edit`/`Write` to `acdsl/**` or `**/*.acdsl` — in every repo, since this file is synced globally (FACT-REPO-ARCH-001). This release deletes those four `ask` entries and relies entirely on the new `acdsl-policy-guard.sh` hook, which is a **no-op in `free` mode**. Since smine's own `acdsl/policy.json` is (by design, D8) `mode: "free"`, an agent working in the smine repo itself — the one repo whose rules and registry get shipped to every target via `Dist` — now has **zero friction** editing `acdsl/registry.json`, `rules.acdsl`, or `evalgen.json`: no ask, no deny, straight through under the existing `defaultMode: acceptEdits`. Before this release, at minimum a human had to see and approve such an edit. The stated purpose of this whole feature is closing "an agent can add ad-hoc rules and verifiers freely" (plan Context) — this change reopens exactly that door in the one repo that is deliberately left ungated. This may be an intentional trade (hook > ask, in the implementer's judgment), but it's a real behavior change that isn't in the plan's Changes section or Decisions table anywhere, and it should be confirmed rather than discovered later. Minimum fix: restore an `ask` (or `permissions.deny`, if that's acceptable for a dev repo) entry scoped to the free-mode case, or add a lighter-weight advisory hook step for free mode.
2. **The row-level verdict cache in `print_agent_worktrees_status.sh` doesn't trace to any plan as new infrastructure.** The `repos-routines-improvements` plan's Current-State fact C3 describes this cache (with specific line-number citations) as pre-existing, needing only a version-salt bump (D3) for the new squash layer. But `git log` shows the entire caching subsystem — `WTS_CACHE_DIR`, the `mkdir`, the atomic `mktemp`+`mv` write, the candidate-tip digest, the deleted-branch pruning sweep — lands in the *same single commit* as the squash layer, and the base commit (`b4981b88`) has zero cache code for this script. Either the plan's baseline fact was hallucinated against a state that didn't exist at review time (a plan-quality defect worth fixing in the authoring skill), or a second, undocumented feature (essentially matching ACTION-IMPL-ARCH-001/ACTION-REVIEW-SPEC-005 "does this concept trace to a requirement") was folded in without its own plan entry. The code itself is solid and well tested (see Strengths), so this is a process/traceability finding, not a functional one — but it's exactly the kind of untraced-concept addition the review doctrine asks to be flagged for confirmation.
3. **`internal/server/repos.go`'s diff carries changes from at least three different plans that aren't all individually traceable to their own plan's Scope.** The client-side worktree-filter rewrite (`worktreeFilter.Query` → `worktreeFilter.Value`, removing the `?base=&kind=` query-param mechanism entirely) and `worktreeSessions`/`peek.SessionIndex` wiring aren't mentioned in the `repo-cache-reload` plan (whose Scope explicitly says "Out... no template or JS changes at all in the final scope") even though they land in the same file the plan claims to own; nor are they in `repos-routines-improvements`. Likely these belong to `peek-multiple-profiles` or `plan-format-viewer-fixes`, neither of which I found text for describing this specific filter-UI rewrite. This is not a functional defect — the change works and is reasonable — but the plan-to-diff traceability for this one file is weaker than for the rest of the release, and it's the kind of drift ACTION-IMPL-ARCH-001 exists to catch before it compounds across a multi-plan release.
4. **`GitRevParse` (`internal/acdsl/git.go:78`) is dead code.** It's specified in the ACDSL policy plan's git-helpers list and implemented, but `policyBase` calls `GitMergeBase` directly and never calls `GitRevParse` to pre-validate a candidate ref — the only caller is its own test (`git_test.go:13`). Either wire it in (e.g. to short-circuit `policyBase`'s candidate loop before attempting a merge-base) or remove it — ACTION-REVIEW-QUALITY-004 (no unnecessary/dead code).

### Minor (Nice to Have)

1. `internal/server/bootstrap.go` is introduced as a **new file** in this diff, but the `bootstrap-profile-improvements` change plan's Context and Current-State sections describe it as already existing (`bootstrap.go:83-85`, with an existing `bootstrapSkillArgs`) and frame the work as a modification. Both the original single-`claude -p` version and its wrapper-based rewrite land within this same release range, so nothing is actually wrong — but a `change` route plan describing a "current state" that never shipped outside this same branch is a slightly confusing plan-authoring pattern worth a note for next time (a `new` route more accurately reflects reality when the "before" state is itself unreleased).
2. `acdsl-policy-guard.sh`'s command-injection heuristic for detecting `cat <ctx-file>` (excluding `;|&<>$` \`'"()`) doesn't account for glob characters — `cat some*file` can pathname-expand to more than two words and silently evade the `[ "$#" -eq 2 ]` check. Low stakes (this hook is an advisory nudge, not the authoritative enforcement layer — `acdsl check`/the read-gate still exist independently), but worth a one-line comment noting the gap is accepted rather than accidental, if it's already understood.
3. `policyBase` (`internal/acdsl/policy.go:195`) derives `isBoundary` from a straight `branch != baseName` string compare with no handling for a fully detached HEAD (`GitBranch` returning `"HEAD"` or empty in that case, per existing `GitBranch` semantics) beyond the incidental fact that `"HEAD" != "main"` happens to evaluate the right way. Works today, but a comment stating this is deliberate (rather than an oversight) would help the next reader trust the edge case was considered.

## Recommendations

- Reset the assigned `arm-wt` checkout's stray uncommitted `acdsl/*` edits before it's reused — they currently make `make audit`/`go test ./...` report a false failure unrelated to any commit.
- For a release this size bundling 9 independent change plans, a short cross-plan "file ownership" pass (which plan owns which hunk of a shared file like `repos.go`) would have caught finding #3 above before merge — most of the plans already do this well individually (explicit `Not changed` bullets), the gap is only at the seams between plans touching the same files.
- Consider whether the `acdsl-policy-guard.sh` no-op-in-free-mode behavior for smine's own repo was meant to fully replace the manual `ask`, or whether it was an unintended side effect of copying the settings.json diff — this is the one item in this release that touches the actual safety story the whole ACDSL-policy feature exists to deliver, so it's worth an explicit yes/no rather than silence.

## Assessment

**Ready to merge?** With fixes (Important #1 needs an explicit decision; #2–#4 are traceability/hygiene items that can be resolved with a one-line changelog note or a follow-up commit).

**Reasoning:** Every piece of code I inspected is correct, matches its plan closely where a plan traces cleanly, is fail-safe in the places that matter (removal-safety gate, policy engine base-authority), and is backed by real tests that I independently confirmed pass on a clean checkout of the head commit. The blocking concern is not a bug but a governance question: the one global settings change that removes the pre-existing manual confirmation gate for ACDSL rule/registry edits — in the one mode (free) where the new automated enforcement provides none — needs a stated decision, because it's exactly the failure mode this whole release's centerpiece feature was built to close.
