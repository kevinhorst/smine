Full test coverage matching every planned case (`TestRegistryRefreshOnExternalEdit`, `TestRegistryAddPreservesExternalEdit`, `TestFingerprint`, etc.). This is the strongest part of the release.
- **`cmd/bootstrap/run.sh`**: matches the bootstrap-profile-improvements plan's full example implementation closely, including the bash 3.2 discipline (`${flags[@]+"${flags[@]}"}`, `if`-guarded expected failures, no heredoc-in-`$()`), MSYS pathconv fix, and the "orchestrate always runs as terminal judge" contract.
- **`internal/routines`** default-disabled/enabled override handling (`overrideLabels`) and the `RunResult`/`IsRunning` "started" marker superseding logic are clean, well-commented, and backed by table-driven tests with real fixtures.
- `go build ./...` and `go vet ./...` are clean across the whole tree.
- The acdsl policy engine (`internal/acdsl/policy.go`) actually *improves* on a flaw in its own plan: the plan's literal example code short-circuits `CheckPolicy` on `policy.Mode == PolicyModeFree` using the *working-tree* policy, which would let an agent bypass every check by simply setting `mode: "free"` in its own uncommitted/committed edit. The shipped code instead re-resolves the policy from the base ref (`basePolicy`) and treats that as authoritative, with a test (`TestCheckPolicyBaseModeSurvivesWorkingWeakening`) proving the base gates even when the working copy is deleted. Good catch by the implementer — see the Critical finding below for where this defense still has a gap.

## Issues

### Critical (Must Fix)

**1. `acdsl/policy.json`'s `base_ref` field lets an agent branch fully bypass gated/strict enforcement — confirmed exploitable.**

- File: `internal/acdsl/policy.go:195-219` (`policyBase`), consumed by `CheckPolicy` at `internal/acdsl/policy.go:329-376`.
- What's wrong: `policyBase` computes `isBoundary` (whether the current branch differs from "the base branch, where humans work") using `policy.BaseRef` — but `policy` here is the *working-tree* policy passed in from `LoadPolicy(root)` (`cmd/acdsl/main.go:114-121`), i.e. attacker-controlled content on the agent's own branch. If an agent commits `acdsl/policy.json` with `"base_ref": "<my-own-branch-name>"` (a value it always knows — it's the branch it's running on), then:
  - `GitMergeBase(HEAD, "<my-own-branch>")` trivially returns `HEAD` (a branch is always its own ancestor).
  - `GitBranch()` returns the same name.
  - `baseName == branch` → `isBoundary = false`.
  - `CheckPolicy` hits `if !isBoundary { return nil, nil }` at line 344-346 and returns **with zero diagnostics**, before `surfaceDelta`, `overlayViolations`, or `ruleDelta` ever run — even though `acdsl/policy.json` itself is nominally protected by `policySurface` (line 31-36), that protection is never reached.
  - This defeats the doc comment's own claim at line 325-328 ("a branch cannot weaken the mode by editing or deleting the working policy.json") — it can, via this one field, and it hides *every other* violation in the same commit (a forbidden `PLAN`-scope rule addition, a `registry.local.json` bypass, anything).
- Why it matters: this is the entire point of the acdsl-policy-modes feature — "the loosy-goosy-rules failure mode is structurally closed" (plan TLDR) and "the enforcement must not be neutered by the thing it guards ... no policy file that can sanction its own edit" (plan Context, Constraint). This specific field is exactly that: a field inside the guarded file that controls whether the guard runs at all.
- Verified: I reproduced this with an executable Go test against a scratch copy of the package (not committed anywhere) — a gated base repo with a protected `ACDSL-PLAN-100` rule; on a branch, adding a forbidden `ACDSL-PLAN-999` rule alone is correctly flagged (2 diagnostics); adding `base_ref: "<own-branch>"` to `acdsl/policy.json` in the same or a later commit makes `CheckPolicy` return 0 diagnostics against the identical forbidden rule still on disk.
- Not covered by any existing test: `TestCheckPolicyUnresolvableBase` only exercises `BaseRef` set to a *non-existent* ref (hard-error path); no test exercises a self-referential `base_ref`.
- How to fix: `isBoundary`/`base` must be derived without trusting any field from the *working* policy. Concretely: resolve `base` once using only the fixed candidate chain (`origin/HEAD`, `origin/main`, `main`, `master`), independent of `policy.BaseRef`, for the purpose of computing `isBoundary` and locating the authoritative `basePolicy`; then let the *base-ref* policy's own `BaseRef` (if any) be used for anything else base-derived. In other words, `base_ref` as an override should only ever come from the already-authoritative (base-committed) policy, never from the working copy being gated. This likely means restructuring `policyBase`/`basePolicy` so base resolution happens in two steps: (a) resolve the *default* base once, unconditionally; (b) re-resolve using the *base policy's* `BaseRef` only if that differs, then re-derive `isBoundary` from that.

### Important (Should Fix)

**2. A new mandatory-skill-invocation enforcement mechanism (`cmd/hooks/skill-invoke-gate.sh`) ships with no corresponding plan, and silently reverses a previously plan-documented, tested decision.**

- Files: `cmd/hooks/skill-invoke-gate.sh` (new, 85 lines), `cmd/hooks/read-gate.sh:76-96` (subagent exemption narrowed — a real behavior change to an existing enforcement hook, not additive), `settings/claude_code/settings.json` (new PreToolUse registration), `skills/quality/railroad-review/changelog.json` (v8.4 entry).
- What's wrong: the only plan touching railroad-review's lane-context behavior in `plans/v1-2-1/` is `2026-08-26-railroad-review-observability-wip-5158764`, whose entire Decision D1 and Scope are "restore CTX-002... via the hook's existing `--no-context` token" and explicitly list "Not changed: skill-context.sh / read-gate.sh: the hooks stay as-is; the fix rides the existing opt-out token." That plan shipped as v8.3 (`skills/quality/railroad-review/changelog.json`'s 8.3 entry matches it exactly). The v8.4 entry in the same changelog then **reverses** v8.3 ("the v8.3 `--no-context` suppression is removed... every lane gets all the review context") and introduces the entirely new `skill-invoke-gate.sh` mechanism plus a change to `read-gate.sh`'s subagent handling — none of which appears in any plan document under `plans/v1-2-1/`.
- Why it matters: this is exactly the "untraceable concept" case the repo's own doctrine calls out (ACTION-REVIEW-SPEC-005 / CLAUDE.md's plan-first workflow routing) — a new PreToolUse hook that can deny tool calls repo-wide based on a `REQUIRE-SKILL:` marker in the first user message, plus a change to how `read-gate.sh` treats every subagent in every skill (not just railroad-review), landed with a v8.3→v8.4 reversal and no design record of why the v8.3 approach (documented, decided, tested) was abandoned one round later. It is plausibly a good change (it is unit-tested — `cmd/tests/test_skill_invoke_gate.sh` exists), but a security/session-behavior-affecting hook with no plan trail is a process gap, and the reversal specifically should have been a Changelog/Decision entry on the observability plan (which it wasn't) or its own change plan.
- How to fix: not a code fix — either backfill a change plan (or append the reversal + new hook rationale to the existing plan's Changelog, per `RULE-PLAN-049`) so the decision is traceable, or confirm with the author this was deliberately fast-followed outside the plan process.

## Recommendations

- Add the `base_ref` self-reference case explicitly to `policy_test.go` once fixed (mirroring the PoC above) so it stays closed.
- Consider whether `policyBase`'s reliance on *any* field from the pre-boundary-check policy is sound as a pattern — the fix for #1 removes `BaseRef` from that path, but it's worth double-checking `AllowTaskContracts`/`EditableScopes` aren't similarly read before `basePolicy()` supersedes them anywhere else in the call graph (I did not find another instance, but the shape of the bug — "trust the working copy before the base copy has spoken" — is easy to reintroduce).
- The skill-invoke-gate / read-gate change (#2) affects every skill's subagents, not just railroad-review's. Worth a short retrospective doc even if not a formal plan, given how broad its blast radius is relative to its one-line mention in a changelog.

## Assessment

**Ready to merge?** With fixes.

**Reasoning:** The bulk of the release (repo-cache-reload, bootstrap wrapper, routines) is well-executed and matches its plans closely, with good test coverage and a clean build. But the acdsl self-management "gated"/"strict" policy feature — the headline security-adjacent addition in this release — has a confirmed, easily-triggered bypass that defeats its entire purpose; that must be fixed before this ships as a security boundary anyone relies on. The skill-invoke-gate/read-gate change should at minimum get a plan/changelog paper trail before merge, though it is not itself shown to be broken.
