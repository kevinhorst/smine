## Strengths

- **`internal/repos/registry.go` read-through rewrite (DR1) is exactly right.** `readRegistrySnapshot` stats before reading (a write racing the read is caught on the *next* stat, never silently missed), `Add`/`Remove` re-read the file fresh under the write lock before applying their delta (a stale in-memory slice can never be written back — this is the actual fix for the "deleted repo comes back" bug), and `save` records the post-write identity so a self-write never triggers a spurious reload. `TestRegistryDeleteStaysDeletedAcrossInstances` and `TestRegistryAddPreservesExternalEdit` directly exercise the regression this fixes.
- **`statusCache` fingerprint invalidation (DR2-DR4)** is a clean, cheap, deterministic answer to "when does the cache reload" — two fast git reads (`for-each-ref` + `worktree list --porcelain`), no TTL, degrades to a re-scan on any fingerprint error. `DropBranches` deliberately keeps the *pre-removal* fingerprint so the next plain load's mismatch forces the re-scan that converges to ground truth — a genuinely clever way to make the optimistic-delete UI and the cache agree without coupling them.
- **`peek.SessionIndex`** (branch-keyed + cwd-keyed session attribution) correctly fixes the pool-worktree-recycling misattribution described in the review's own context facts, with a sensible branch-first/cwd-fallback order in `worktreeSessions` (`internal/server/repos.go`).
- **`internal/acdsl/policy.go`** is a well-designed, well-documented self-management gate: the base-ref policy is authoritative over the working copy specifically to prevent an agent branch from weakening its own governance by editing `policy.json`, the write-time hook (`acdsl-policy-guard.sh`) and the git-diff-based Go check are correctly layered (fast UX feedback vs. authoritative backstop that also covers Bash-based edits the hook doesn't intercept), and `acdsl/README.md`'s "Modes" section documents the exact hard-fail-over-silent-bypass tradeoff the code implements.
- Shell scripts consistently follow the `set -uo pipefail` (not `-e`) discipline with guarded `read`/subshell failures (`|| true`, `|| answer=n`, `${arr[@]+"${arr[@]}"}` for empty-array-under-`set -u`) — e.g. `cmd/hooks/skill-invoke-gate.sh`, `routines/smine-nightly/run.sh`.
- Good test coverage on the highest-risk change: registry_test.go adds targeted regression tests for exactly the cross-instance/external-edit scenarios the bug report described, not just happy-path coverage.

## Issues

### Critical (Must Fix)

### Important (Should Fix)

- **`cmd/hooks/skill-invoke-gate.sh:42`** — the invoked-via-prompt-start check is a bare glob prefix match: `case "$first_user" in "/$required"*) invoked=1 ;; esac`. This matches any first message that merely *starts with* `/$required`, not one that invokes exactly that skill. In this repo, `smine` is both a real skill name and a literal prefix of nine other skills (`smine-batch`, `smine-apply`, `smine-consolidate`, `smine-context`, `smine-memory`, `smine-orchestrate`, `smine-permissions`, `smine-routines`, `smine-skills`, `smine-style`). A lane whose transcript sets `REQUIRE-SKILL:smine` but whose first message is `/smine-batch ...` would incorrectly pass the gate as "invoked", skipping the enforced-skill-first contract the hook exists to guarantee. Today's only call site (`REQUIRE-SKILL:railroad-review` in `railroad-review.js`) has no colliding prefix, so this is latent, not live — but the hook is written as general-purpose infrastructure (arbitrary `[a-z0-9-]*` skill name) and this exact smine family is the most obvious place it would bite next. Fix: require a word boundary after the name, e.g. `case "$first_user" in "/$required" | "/$required "*) invoked=1 ;; esac`. Not covered by `cmd/tests/test_skill_invoke_gate.sh` (only exercises `railroad-review`) — worth a regression case for a required name that is a prefix of another skill's name.
- **`internal/server/repos.go` — deferred grant asymmetry remains unaddressed.** `handleReposAdd` grants `permissions.additionalDirectories` when adding a repo; `handleReposDelete` never revokes it (confirmed in the current diff — `handleReposDelete` only calls `Registry.Remove` and `statusCache.Delete`). This is explicitly called out as a known, accepted gap in the repo-cache-reload plan's "Deferred findings" section, so it's not a silent regression — but it is genuine, real dead-permission accumulation (a deleted repo's directory stays grantable/readable indefinitely) and per ACTION-REVIEW-DOCS-004 this should be a tracked open item somewhere more durable than a plan's "Deferred findings" bullet (an issue, a TODO with an owner, something that outlives the plan directory once it's archived), not just left to be rediscovered.
- **`routines/smine-orchestrate` autonomous merge-to-main-and-push** is granted `Bash(git *)` (unrestricted git subcommand access) in its frontmatter, and the nightly wrapper invokes it unattended with `--permission-mode acceptEdits`. The skill's own hard invariants (never push without a remote, never add a remote, mechanical postcondition re-verification in the wrapper independent of the agent's self-reported status) are a reasonable belt-and-suspenders design, and I don't think this needs to block the release — but a wildcard `Bash(git *)` for a skill whose job is "merge and push to origin/main unattended, judging content it doesn't fully control (mined session data, other agents' proposals)" is a wider blast radius than the documented duties need (`merge --no-edit`, `push origin main`, `status`, `merge-base --is-ancestor`, `log`, `remote get-url`). Consider narrowing the allowlist to the specific subcommands actually used, especially since this same file already narrows other tools' allowlists deliberately (`Bash(make audit *)`, `Bash(go run ./cmd/acdsl *)` rather than bare `Bash(*)`).

### Minor (Nice to Have)

- **`Makefile:81`** — the new `build-install` target's doc-comment is copy-pasted verbatim from `build` (`## build: build all binaries and install`) instead of being renamed to its own target (`## build-install: ...`). `make help` greps `^##` lines and will print two entries both labeled `build`, one of them describing the wrong target. One-word fix.
- **`internal/server/profilesettings.go:209-217`** (`styleTestTarget`) joins an admin-configured `ROUTINE_TOKEN` env value directly into `filepath.Join(s.tokenDir, label)` with no validation that `label` stays within `tokenDir` (no rejection of `../` or absolute-looking values) before reading it and feeding its contents to `claude -p` as an OAuth token. Low severity given this is a single-operator local tool and the value comes from the operator's own routine config rather than an HTTP request body, but worth a `filepath.Clean` + prefix check if that env ever becomes reachable from a less-trusted input path.
- `.gitignore` still ends without a trailing newline (pre-existing, not introduced by this diff, but the diff touches the same lines and could have fixed it in passing).

## Plan Alignment

- The repo-cache-reload plan (the one plan I could verify in full detail) is implemented essentially as specified: registry read-through, fingerprint-gated status cache, dead single-branch-remove endpoint deleted, optimistic delete UX untouched. I want to flag one thing explicitly for confirmation rather than silently accept it: the plan's Hot Items section states "no template or JS changes at all in the final scope — the UI is untouched," yet the reviewed diff range does contain a substantial rework of `_worktree_status.html`/`repo_detail.html` (query-param server-side filtering replaced by client-side JS filtering with `data-kind`/`data-base` attributes, a new Reload button, a new "cached" timing marker). I traced this and believe it actually belongs to the earlier `2026-08-27-repos-routines-improvements` plan (whose Behavior Contract explicitly lists `?refresh=1` semantics / scan timing / Reload button / filter chips as pre-existing, "must not change" state as of *its* writing) rather than being new work introduced during repo-cache-reload — the two plans' timestamps and content are consistent with that read. I'm calling it out because the diff range I was given spans both plans (and the whole 1.1.4→1.2.1 release) squashed together, so I can't fully rule out the ordering from git history alone; if repo-cache-reload's own commits did in fact touch this UI, that plan's "no UI changes" claim is inaccurate and should be corrected in its Changelog.
- Everything else I checked at Decisions/Changes granularity (acdsl policy modes, peek multi-profile session attribution, smine-profile-settings' casual/dev-mode wiring into `smine-nightly/run.sh`) matches its plan's stated target state; I did not do an exhaustive fact-by-fact reconciliation on the other eight plans given the size of the range.

## Recommendations

- Add the missing `skill-invoke-gate.sh` prefix-collision regression test alongside the fix.
- Move the `additionalDirectories` revoke-on-delete gap from a plan's "Deferred findings" bullet into a durable tracked item (issue/TODO with context/facts note) before that plan directory gets archived — plan dirs leave the code repo on merge (RULE-PLAN-073) and the gap would otherwise become undiscoverable.
- Given `smine-orchestrate` is new, unattended, and merges+pushes to `main`, it'd be worth a short soak period (bootstrap mode / a handful of manual-triggered runs) before it's relied on for fully unattended nightly operation, if that isn't already the plan.
