Permission System

Every tool call is allowed by a rule or read-only analysis, or denied with a reason. Nothing prompts.

The tool-policy gate (cmd/toolpolicy) hooks every tool call, permission request, prompt submit, Skill result and mid-session directory add, in every host (terminal, Desktop, headless, subagents) and mode. Its settings: Settings § Permission gate.

The closed world

Fails open

Plan rules

A plan's rules live in plans/<feature folder>/<plan dir>/permissions.json (git-ignored): rules (each rule, target, needed_for) and checked. Never in, or read from, the plan file. Outside plan mode, smine-rules plan-display <plan file> <session plan file> writes plan plus rules into the session plan file under ~/.claude/plans/, the display copy. That directory is global, not a repo's plans/: it works across sessions, so a plan and its rules survive a hand-off to another session.

  1. The design run freezes the file

    toolpolicy freeze plans/<feature folder>/<plan dir> records the file, even an empty set, in ~/.claude/tool-policy/frozen.jsonl and applies its rules to that worktree. Each rule passes the self-service shape check and equals the gate's narrowest rule for its target.

    toolpolicy freeze plans/2026-10-02-x-7ea30b5/2026-10-02-x-wip-7ea30b5
  2. One freeze per typed design prompt

    One per /fdesign prompt you typed, one per unattended design run. Refreezing needs such a prompt naming the plan file. The rules file is write-protected except in a session that may still freeze its plan.

  3. A typed /fimplement is the code gate's approval

    Plan at its code gate, no record, session may still freeze it: the hook freezes it on that prompt (same checks), noted in the report's approval: line. The word counts anywhere in the prompt (later line, mid-sentence, pasted block); the freeze lands at prompt submit, before the agent acts. Never: a prompt opening with another harness tag (cross-session message), a Skill(fimplement) call.

  4. Every /fimplement applies the record

    /fimplement <plan file name> applies it to the anchor's settings.local.json, any worktree. Plan: the first argument word naming a plan file (arguments: all after the command, line breaks included, as the harness splits them); else the plan this session last ran smine-rules plan-sections on (a design run's one plan record, forced by fdesign's enforce block before the code gate's turn ends); neither: best-effort. A master plan applies every derived plan whose master: link names it, in one write one toolpolicy revert undoes. No record: nothing applied, the run continues.

    tool-policy /fimplement hook:
- plan: …/plans/2026-10-02-x-7ea30b5/2026-10-02-x-wip-7ea30b5/design/x.md
- Permissions: appended 2 rule(s), 0 already present — Bash(lsof *) Bash(./bin/heartbeat serve *)
Note

Nothing waits on a freeze: neither smine-rules plan-sections nor any skill refuses an unfrozen plan.

How a call is decided

Checks run in this order on every PreToolUse call; the first answer wins.

#CheckThen
1ExitPlanMode?The engine decides: plan approval stays yours.
2Denied tool, or a deny rule matches?Deny.
3Breaks an invoked skill's enforce gate rule?Deny.
4Workflow with a marked non-primer script, or a launch after a typed turn outside a notification-opened turn?Deny (launch guard below).
5Agent without an explicit non-Fable model?Deny.
6Ungated built-in?Allow.
7Bash, PowerShellPath fence → read-only? → one pipe? → settings rule → skill grant. A match allows, no match denies.
7Read, Glob, GrepInside the read roots or a skill path grant.
7Edit, Write, NotebookEditInside the write roots and not protected.
7Rule-bearing: WebFetch, WebSearch, Skill, Agent, Workflow, Monitor, Artifact, EnterWorktree, mcp__*A settings rule, a skill grant, or a Skill call for an active skill or one your newest message names.

What counts as your message

Counts: a typed prompt (turnOrigin: human, every text block) and a message typed mid-turn (queued_command attachment, human origin, no meta mark): interruptions, their addenda and runs of interruptions all arrive as such rows. A Desktop paste wrapper drops with its body wherever it sits: no command inside a paste counts, a pasted transcript fires nothing; typed text around it counts.

Never counts (internal/transcript.Classify): hook block reasons written back as user rows (isMeta, "Stop hook feedback:", above all the session-title hook's rename instruction), the [Request interrupted by user] marker, tool results, compaction summaries, local commands like /model, peer relays, task notifications, headless prompts.

The gate reads commands from the transcript on every call, plus the submitted prompt. A mid-turn #add counts at the agent's next tool call; a #set rule is written on that call and admits it. A submitted prompt prints one result line per command as context; mid-turn messages apply silently. The file is the applied state: already reflected messages write nothing; toolpolicy revert never touches these entries. Claude Code's DirectoryAdded hook (/add-dir, the SDK's register_repo_root) runs the gate, appending that directory likewise; --add-dir and the Desktop "+" raise no such event.

Cards the gate cannot reach

The gate's PermissionRequest answer covers only what Claude Code asks through that hook; cards the Desktop app raises itself are controlled in its Settings.

  • Browser pane cards: per-site consent; "submit sign-in credentials" for a URL with embedded credentials (kept away by the gate's deny of that URL form).
  • ccd_* approval cards.
  • Unlisted Desktop MCP servers: denied by the gate; admit by rule.
